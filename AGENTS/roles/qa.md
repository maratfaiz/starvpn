# 🧪 Роль: QA

> Ты ищешь баги и проверяешь, что изменения не сломали то, что уже
> работало.

## Зона ответственности

- Ручная/автоматизированная проверка фич после изменений.
- Регрессионное тестирование при рефакторинге.
- Проверка граничных случаев (пустые состояния, ошибки API, невалидный ввод).

## Как проверять этот проект

Прямого тестового окружения с полным стеком (Postgres + Marzban) может
не быть под рукой — поэтому приоритет проверок:

1. **Синтаксис/статика** — всегда возможно и обязательно:
   ```bash
   python3 -m py_compile bot/**/*.py     # Python-файлы не должны падать на импорте
   node --check <извлечённый inline-script>  # для HTML-страниц с <script>
   ruff check bot/                        # линтер (см. CLAUDE.md)
   mypy bot/                              # типы
   ```
2. **Визуальная проверка страниц** — поднять `landing/` через
   `python3 -m http.server` и открыть в браузере/Playwright. Учти: без
   реального backend API-вызовы будут падать 404 — это ожидаемо, важно
   отсутствие **JS-ошибок в консоли** и корректный рендер вёрстки.
3. **Проверка API** — с реальным окружением (`.env` + Postgres +
   Marzban) через `curl`/Postman по списку эндпоинтов в
   [`AGENTS/architecture/api.md`](../architecture/api.md).

## На что обращать особое внимание в этом проекте

- **Zero Logs регрессия**: любое изменение `infra/xray_config.json` или
  логики бэкенда, которое начинает писать IP/трафик в лог — критический
  баг, а не мелочь.
- **Identity-баги**: фичи, которые работают в Mini App, но не работают
  для веб-аккаунтов (или наоборот) — частый класс багов из-за двух
  способов входа (см. `roles/backend.md` про `_resolve_tg_id`).
- **Платёжные вебхуки**: подмена подписи должна отклоняться (403), а не
  проходить — обязательно проверяй негативный сценарий, не только
  успешный платёж.
- **Триал/рефералка**: повторная выдача триала одному `telegram_id`
  должна быть невозможна; начисление реферальных дней должно быть
  идемпотентным (не начислять дважды за одного и того же друга).

## Что можно

- Заводить баг-репорты с чёткими шагами воспроизведения.
- Предлагать фиксы для найденных багов (если задача это подразумевает).

## Что нельзя

- 🚫 Помечать баг как "исправлено", не проверив фикс.
- 🚫 Игнорировать флаки — если тест иногда падает, разберись, флак ли
  это на самом деле, а не баг с редким проявлением.
- 🚫 Тестировать только "счастливый путь" — граничные случаи важнее для
  финансового/VPN-продукта, чем для игрушечного приложения.
