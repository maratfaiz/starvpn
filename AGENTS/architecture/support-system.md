# Support System

> DM-контакт на реальную систему заявок и убрать вместо-чата в админке
> одноразовый `admin_reply` на настоящий тред с приоритетами и

## Точки входа

Раньше под словом «поддержка» скрывались три несвязанных канала:
кнопка в боте, тайл в Mini App и форма на сайте — причём первые два вели
на голый DM `@hashprojects`, в обход системы заявок целиком, и она
реально работала только для тех, кто пришёл с сайта.

Теперь все три ведут в одну и ту же систему:

1. **`/support`** (сайт, форма, вход не нужен) — как и раньше, создаёт
   заявку через `POST /api/support`.
2. **Бот, кнопка «🎧 Поддержка»** (`bot/handlers/start.py`) — теперь не
   пишет "напиши администратору", а даёт inline-кнопку со ссылкой на
   `{SITE_URL}/support`.
3. **Mini App, тайл «Написать в поддержку»** (`AccountScreen.jsx`) —
   открывает тот же `{SITE_URL}/support` через `tg.openLink` вместо
   `tg.openTelegramLink` на DM. `GET /api/me`'s `support_url` — тот же
   адрес (не DM), это то, что реально должно прийти в продакшен-фронтенд,
   когда он подключится к настоящему API.

**2026-09-03, тот же день, ещё одна правка:** голый `@hashprojects`-DM
убран отовсюду насовсем, включая fallback-упоминания. Раньше
`settings.support_username` оставался в 2-3 местах как аварийный
контакт (`bot/handlers/dashboard.py` — ссылка недоступна;
`bot/handlers/admin.py` — текст при бане; `bot/utils/wiki_page.py` —
подвал сгенерированных wiki-страниц) — по прямому запросу "уберём
поддержку по чату и сделаем всё по тикетам" все три переведены на
`{SITE_URL}/support`, а само поле `support_username`/`SUPPORT_USERNAME`
удалено из `bot/config.py`. Теперь **нет вообще ни одного места в
кодовой базе**, которое даёт пользователю прямую ссылку на личный DM
администратора — единственный путь для нового обращения это тикет.
Не путать с тем, что человек может просто написать `@hashprojects`
напрямую в Telegram сам, зная контакт заранее, — это ограничение
платформы (Telegram не даёт "отключить" личные сообщения по имени
аккаунта), а не то, что можно починить кодом.

## Модель данных

- **`support_tickets`** — карточка заявки: кто (`user_id`/`contact`),
  о чём (`topic`, снимок исходного текста в `message`), `status`
  (open/answered/closed), **`priority`** (low/normal/urgent, новое),
  **`assigned_admin_id`** (новое, FK на `admin_accounts`),
  **`last_message_at`/`last_message_sender`** (новое, денормализовано —
  на них строится бейдж "новое от клиента" и сортировка списка в
  админке, без join'а на историю сообщений на каждый список).
- **`support_ticket_messages`** (новая таблица) — вся переписка:
  `ticket_id`, `sender` (`user`/`admin`), `admin_id`/`admin_username`
  (кто из админки ответил), `body`, `created_at`. Первое сообщение
  вставляется при создании заявки (тот же текст, что в
  `support_tickets.message`) — так вся история, включая самое первое
  сообщение, лежит в одном месте, а не размазана между двумя таблицами.

**Что было раньше и почему поменяли:** один-единственный текстовый
столбец `admin_reply` на тикет. Второй ответ физически стирал первый —
то есть переписка из более чем одного сообщения от поддержки была
невозможна, и в админке был просто "виджет из одного вопроса и одного
ответа", а не подобие тикет-трекера. Миграция `0015_support_ticket_threads`
переносит существующие `message`/`admin_reply` в первые строки нового
треда и удаляет `admin_reply` насовсем.

## Двусторонняя переписка через бота

Если админ отвечает через админку и у автора заявки реальный
(положительный) `telegram_id`, сообщение в боте приходит с inline-кнопкой
**«✍️ Ответить»** (`callback_data=f"ticket_reply:{id}"`). Нажатие
переводит `bot/handlers/support.py` в FSM-состояние
`SupportForm.waiting_reply` (см. `bot/states/payment_states.py`) с
`ticket_id` в data — следующее текстовое сообщение пользователя, каким
бы оно ни было, уходит в тред как `SupportTicketMessage(sender="user")`,
переоткрывает заявку (`status="open"`) и очищает состояние.

Для веб-аккаунтов (синтетический отрицательный `telegram_id`) и
анонимных обращений с email-контактом ответ уходит на почту
(`bot/utils/mailer.py::send_ticket_reply_email`) — без кнопки, это
осталось одноразовым письмом, как и раньше. Обратного канала (парсинг
входящих писем) нет и не планировался — у email просто нет aiogram-FSM,
а строить отдельный inbound-mail пайплайн ради этого не было запроса.
Для `@username` без привязанного аккаунта Bot API написать вообще не
даёт — эти заявки остаются на ручной ответ через сам контакт, как и
до этой правки.

## Админка (`admin/index.html`, раздел «Обращения»)

> **2026-09-03, тот же день, следующая правка:** первая версия рендерила
> список карточками и тред — messenger-стиля bubbles (`.msg-bubble`,
> выравнивание influenced по отправителю). По явному запросу переделано
> на обычную таблицу заявок (те же `.tbl-wrap`/`.tbl-scroll`/`.tbl-foot`,
> что и у Пользователей/Платежей/Рефералов) + плоский лог сообщений
> внутри деталей (`.tkt-log-row` — полная ширина, различие только
> цветной полоской слева и подписью, без "пузырей" и выравнивания по
> сторонам). Логика/эндпоинты не менялись, только разметка и CSS.

- Список: точка статуса, бейдж **«Новое»** (последнее сообщение от
  клиента и заявка не закрыта), бейдж приоритета, кому назначена (или
  публичный ID, если не назначена) — сортировка по `last_message_at`,
  не по времени создания.
- Фильтры: статус (было), + **приоритет** (Срочные/Обычные/Низкий),
  + **назначение** (Мои/Не назначены), + общий поиск (см. ниже).
- Деталь: весь тред сообщений (не один вопрос-ответ), переключатель
  приоритета прямо в шапке, «Взять в работу» / «Снять с себя»
  (самоназначение — ответ на неназначенную заявку автоматически берёт
  её в работу отвечающего, чтобы у отвеченной заявки не было формального
  ответа без владельца), закрыть/переоткрыть — как раньше.
- Новые эндпоинты: `GET /web/tickets/{id}` (карточка + тред),
  `POST /web/tickets/{id}/priority`, `POST /web/tickets/{id}/assign`
  (`{admin_id: "me" | <id> | null}`).

**2026-09-03, ещё одна правка тем же днём — «способ связи» + мобильная
версия:**

- Оба тикет-эндпоинта (`GET /web/tickets`, `GET /web/tickets/{id}`)
  теперь возвращают `channel`/`channel_value` — куда реально уйдёт ответ,
  если нажать «Отправить» (`_ticket_channel()` в `bot/api.py`):
  - `telegram` — реальный `telegram_id`, уходит сообщением в бота
    (с кнопкой «Ответить», см. выше).
  - `email` — есть email (свой у аккаунта или указан в форме контактом),
    уходит письмом через `bot/utils/mailer.py::send_ticket_reply_email`
    (обычный SMTP — Gmail-приложение-пароль/SendGrid/Mailgun/Яндекс/что
    угодно, что говорит SMTP; настраивается `SMTP_HOST`/`PORT`/
    `USERNAME`/`PASSWORD`/`FROM` в `.env`; это уже было реализовано
    раньше для кода подтверждения email, просто не было видно в
    интерфейсе тикетов, что ответ реально уйдёт письмом). **Без
    настроенного `SMTP_HOST` письмо не отправится — попадёт только в
    лог** (`mailer.py`'s "SMTP не настроен" warning), это не баг, а
    поведение по умолчанию до того как впишут реальные credentials.
  - `telegram_manual` — в форме указан голый `@username`, но аккаунт с
    таким ником не привязан ни к одному `User.telegram_id` — Bot API не
    даёт написать первым пользователю, который не жал `/start` у бота,
    поэтому автоматической отправки нет физически, только пометка
    "свяжитесь вручную".
  - `unknown` — контакта нет вообще (не должно происходить в норме,
    форма требует `contact` для анонимных обращений).
  - Таблица показывает бейдж «Способ связи» отдельной колонкой; деталь —
    тем же бейджем в шапке + текст под полем ответа меняется по каналу
    (например: `Ответ уйдёт письмом на {email} (через настроенный SMTP)`),
    вместо прежнего одинакового текста для всех случаев.
- **Мобильная версия таблицы заявок**: у общего `.tbl-wrap`/`table` в
  остальных разделах (Users/Payments/...) мобильная адаптация — просто
  горизонтальный скролл (`.tbl-scroll{overflow-x:auto}`). Для заявок
  этого недостаточно для "красиво" — добавлен `.tkt-table` (новый класс
  только на этой таблице, остальные разделы не затронуты) с
  media-запросом `max-width:680px`: `thead` скрывается, `tr` становится
  блоком-карточкой, у каждого `td` есть `data-label` и `::before{content:
  attr(data-label)}` — получается стопка карточек "подпись / значение"
  без переписывания JS-рендера таблицы (те же `<td>`, просто добавлен
  атрибут). Общая раскладка приложения (сайдбар → нижний таб-бар +
  выезжающий "Меню"-шит) уже была мобильно-адаптивной до этой правки —
  раздел "Обращения" получил её бесплатно, т.к. это просто ещё один
  пункт меню.

**Побочный фикс, обнаруженный при подключении общего поиска:**
`goto(section)` безусловно сбрасывал `query = ''` при каждом вызове —
включая вызов из debounce самого поискового инпута (`onQueryInput` сам
же стирал только что введённое значение на каждом ре-рендере). То есть
глобальный поиск не работал вообще ни для одного раздела, который его
использует (`users`, теперь и `support`), а не только для тикетов.
Поправлено: сброс фильтров/`query`/`selectedRow`/`selectedTicket`
происходит только при переходе в **другой** раздел
(`s !== section`), а не при каждом ре-рендере текущего.
