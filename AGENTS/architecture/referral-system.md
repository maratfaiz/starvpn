# Referral System — текущее состояние и предложение по упрощению

> Статус: **черновик на согласование**, код НЕ менялся. Это описание
> того, что есть сейчас, и предложение, что можно изменить — окончательное
> решение (цифры, оставлять ли достижения) должен принять владелец
> продукта. См. `bot/handlers/payment.py::REFERRAL_ACHIEVEMENTS` и
> `_credit_referral()` — вся логика начисления сейчас там.

## Текущая механика (как есть)

Источник правды: `bot/handlers/payment.py`.

1. **Базовый бонус**: `REFERRAL_DAYS_BONUS = 30` дней рефереру за каждые
   `REFERRAL_MILESTONE_SIZE = 2` оплативших реферала. Не ограничено сверху —
   считается по `referrer.referral_count % 2 == 0` при каждом новом
   оплатившем реферале.
2. **Разовые достижения** (`REFERRAL_ACHIEVEMENTS`) — дополнительно, поверх
   базового бонуса, один раз при достижении порога:

   | Порог (оплативших друзей) | Иконка | Название | Бонус |
   |---|---|---|---|
   | 1 | 🥉 | Первая ласточка | +5 дней |
   | 5 | 🥈 | Амбассадор | +20 дней |
   | 10 | 🥇 | Легенда STAR VPN | +50 дней |
   | 25 | 💎 | Партнёр года | +150 дней |

3. Всё выдаётся только в **днях подписки** (`User.extra_days_granted`,
   `_grant_subscription`) — не деньгами, не баллами, не выводится. Это уже
   соответствует принципу "выдаём только дни".

### Проблема: суммарная щедрость

Обе системы складываются. На 25 оплативших рефералов реферер получает:

- Базовый бонус: `floor(25 / 2) × 30 = 360` дней
- Достижения: `5 + 20 + 50 + 150 = 225` дней
- **Итого: 585 дней (~19 месяцев)** бесплатно, без единой собственной оплаты

Для сравнения: самый дорогой платный тариф сейчас — 180 дней за 899 ₽
(`CARD_PLANS.plan_6m`, `bot/utils/robokassa.py`). То есть 25 приведённых
друзей дают реферреру более чем в 3 раза больше дней, чем можно купить
за деньги одним платежом — именно это и было названо "слишком щедро".

## Предложение: только базовый бонус, без надстройки

Убрать `REFERRAL_ACHIEVEMENTS` полностью, оставить один-единственный
принцип: **+30 дней за каждые 2 оплативших друга**, без верхнего предела
и без разовых надбавок сверху.

На 25 рефералов это даёт **360 дней** вместо 585 — сокращение примерно
на **38%**, при этом:

- Система становится проще объяснить пользователю одной фразой (уже
  так и написано в UI: "За каждых 2 друзей — 30 дней").
- Не нужно поддерживать отдельную таблицу достижений, иконки, тексты
  уведомлений о разблокировке.
- Не отменяет уже начисленные дни у существующих пользователей —
  `User.extra_days_granted`/`subscription_expires_at` не пересчитываются
  задним числом, они просто перестают расти по старым правилам.

### Альтернативы (на случай, если совсем убирать достижения не хочется)

Если продукту важно сохранить ощущение прогресса/геймификации:

- **Вариант A — уменьшить бонусы достижений**, например 5 / 10 / 20 / 40
  вместо 5 / 20 / 50 / 150 (на 25 рефералов даёт `360 + 75 = 435` дней —
  тоже заметно меньше 585, но геймификация остаётся).
- **Вариант B — общий потолок**: ввести `MAX_EXTRA_DAYS_GRANTED` (например,
  365) и не начислять сверх него, независимо от формулы. Просто и
  предсказуемо для расчёта себестоимости программы.
- **Вариант C — оставить как есть**, если 585 дней на 25 друзей всё же
  укладывается в экономику продукта (это оценка не автора документа, а
  решение о юнит-экономике, которое должен принять владелец).

## Что менять в коде, когда решение принято

Один источник правды — `bot/handlers/payment.py`:

```python
REFERRAL_DAYS_BONUS = 30
REFERRAL_MILESTONE_SIZE = 2
REFERRAL_ACHIEVEMENTS = [...]   # удалить целиком для "только базовый бонус"
```

и `_credit_referral()` — убрать блок `unlocked_achievement` (строки
~184–192 на момент написания), оставить только начисление за
`REFERRAL_MILESTONE_SIZE`.

На фронтенде (`landing/account.html`, вкладка "Приглашения") блок
"Достижения" (`.badge-grid`, рендерится в `loadReferral()` из
`ref.achievements`) при удалении достижений из бэкенда просто перестанет
получать данные — нужно убрать и сам блок из шаблона, а не оставлять
пустую секцию. `GET /api/referral` в `bot/api.py` тоже перестанет
отдавать поле `achievements` (или будет отдавать пустой список — тогда
фронтенд можно не трогать, он уже проверяет `ref.achievements.map`
только когда массив есть... на самом деле сейчас не проверяет пустоту,
просто мапит — пустой массив даст пустой `.badge-grid`, что тоже нужно
скрыть через `${ref.achievements.length ? ... : ''}`, как уже сделано
для `ref.referrals`).

## Важно для следующего агента

Не меняй `REFERRAL_ACHIEVEMENTS`/`_credit_referral` по этому файлу
самостоятельно — это предложение, а не утверждённое решение. Дождись,
пока владелец продукта явно скажет "внедряй вариант X", и только тогда
делай код + миграцию отображения на фронтенде разом (нельзя менять одно
без другого — рассинхрон бэкенда и `account.html` даст либо пустой
"Достижения" блок, либо JS-ошибку на `.map` от отсутствующего поля).
