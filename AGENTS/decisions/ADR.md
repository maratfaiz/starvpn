# ADR — Architecture Decision Records

Здесь фиксируются решения вида "мы специально сделали X, а не Y, потому
что Z" — чтобы следующий агент не "исправлял" осознанный выбор, приняв
его за случайную недоработку.

**Формат новой записи:**
```markdown
## ADR-00N — <название>
- **Дата:**
- **Статус:** Принято / Пересмотрено (→ ADR-00M)
- **Контекст:** какая была проблема/развилка
- **Решение:** что выбрали
- **Почему не иначе:** что рассматривали и почему отклонили
- **Последствия:** что это значит для будущей разработки
```

Не редактируй чужие записи задним числом — если решение устарело,
добавь новую запись со статусом "Пересмотрено" и ссылкой.

---

## ADR-001 — Один процесс для бота, API и раздачи сайта

- **Статус:** Принято
- **Контекст:** Нужно было решить, разносить ли Telegram-бота, backend
 API и раздачу сайта/админки на отдельные сервисы.
- **Решение:** Всё живёт в одном Python-процессе (`bot/main.py`),
 запускается через `asyncio.gather` (aiogram long polling + uvicorn),
 один Docker-контейнер.
- **Почему не иначе:** Продукт достаточно компактный — разделение на
 сервисы добавило бы сетевые вызовы, отдельные деплои и точки отказа
 без реальной пользы на этом масштабе.
- **Последствия:** Правки сайта/админки не требуют пересборки —
 `_serve_html` читает файлы с диска. Обновление кода бота = один
 `git pull` + рестарт одного контейнера. Не создавай отдельный сервис
 под "ещё один маленький API" — расширяй существующий `bot/api.py`.

## ADR-002 — Веб-аккаунты через синтетический отрицательный `telegram_id`

- **Статус:** Принято
- **Дата:** реализовано в рамках личного кабинета на сайте (магик-линк вход)
- **Контекст:** Нужен был вход на сайт по email, без привязки к
 Telegram — но вся схема БД (Device, Payment, GiftNotification,
 рефералка) была построена вокруг `users.telegram_id` как основного
 ключа.
- **Решение:** `users.telegram_id` остаётся `NOT NULL`. Веб-аккаунт без
 Telegram получает **синтетический отрицательный** `telegram_id`,
 сгенерированный при первом входе по email
 (`webauth._get_or_create_user_by_email`). Реальные Telegram ID всегда
 положительные — коллизий не бывает.
- **Почему не иначе:** Альтернатива — сделать `telegram_id` nullable и
 завести отдельный `web_user_id` — потребовала бы менять внешние ключи
 во всех связанных таблицах и дублировать логику "к какому пользователю
 относится этот объект" в двух вариантах.
- **Последствия:** Проверка "это настоящий Telegram-аккаунт?" —
 `user.telegram_id > 0`. Все существующие эндпоинты, работавшие с
 Telegram-пользователями, автоматически работают и с веб-аккаунтами.
 `_resolve_tg_id()` — единая точка входа, которая скрывает эту деталь
 от остального кода.

## ADR-003 — Сайт и админка: статичный HTML без шаблонизатора и сборки

- **Статус:** Принято
- **Контекст:** Нужно было выбрать технологию для сайта/личного
 кабинета/админки: SPA-фреймворк, серверный шаблонизатор (Jinja2) или
 простой статичный HTML.
- **Решение:** Обычные `.html`-файлы с инлайновыми `<style>`/`<script>`,
 без build step. FastAPI отдаёт их "как есть" с диска.
- **Почему не иначе:** Шаблонизатор/SPA добавили бы шаг сборки и
 зависимость от npm/webpack там, где в этом нет необходимости — эти
 страницы не такие уж динамические, а быстрая правка "открыл файл →
 поправил → сразу на проде" ценнее.
- **Последствия:** Дизайн приходит в виде готовых макетов и
 переносится вручную в существующие файлы (не генерируется шаблоном).
 Не добавляй сборку для `landing/`/`admin/` без отдельного обсуждения —
 см. `AGENTS/roles/frontend.md`.
- **Исключение:** Telegram Mini App (`webapp/`) — это React-проект,
 потому что там реально нужна интерактивность уровня SPA. `webapp/app.html`
 — собранный артефакт, который коммитится в git вместе с исходниками.

## ADR-004 — Zero Logs как жёсткое требование, не настройка

- **Статус:** Принято
- **Контекст:** Продукт позиционируется как приватный VPN — нужно
 решить, насколько строго это применяется технически.
- **Решение:** `infra/xray_config.json` **всегда** имеет
 `"access": "none", "error": "none", "loglevel": "none"`. Нигде в коде
 не логируются IP пользователей, метаданные соединений или трафик.
- **Почему не иначе:** Логирование "для отладки" или "временно"
 создавало бы риск случайно оставить его в проде — поэтому это
 зафиксировано как правило, а не переключаемая опция.
- **Последствия:** Любой PR, который добавляет логирование
 IP/трафика/соединений — блокируется, даже если это "временно для
 дебага". Отлаживай на локальном окружении с явно тестовыми данными.

## ADR-005 — Криптовалюта скрыта из UI, но не удалена из кода

- **Статус:** Принято
- **Контекст:** Оплата криптовалютой (CryptoPay) была реализована, но
 бизнес-решение — временно убрать её из пользовательского интерфейса.
- **Решение:** Код платежей криптой (`bot/utils/cryptopay.py`,
 `/api/invoice/crypto`, `/api/crypto/plans`) остаётся в репозитории.
 Видимость управляется тумблером в `app_settings`
 (`bot/utils/settings_store.py`, ключ `crypto`, по умолчанию `False`).
 Админ может включить обратно через `/admin` → Настройки, без деплоя.
- **Почему не иначе:** Удаление кода означало бы полную переработку при
 возврате функции; тумблер даёт возможность включить/выключить без
 правок кода.
- **Последствия:** Не удаляй крипто-код "раз он не используется" — он
 используется, просто скрыт. Если задача — "убрать оплату криптой" на
 самом деле, уточни у человека: скрыть (уже так) или удалить насовсем.

## ADR-006 — Вход в личный кабинет: email+пароль вместо magic-link

- **Дата:** 2026-08-30
- **Статус:** Принято (пересматривает механизм входа из ADR-002, сама
 схема синтетического `telegram_id` из ADR-002 не меняется)
- **Контекст:** Изначально вход в веб-личный кабинет был passwordless —
 magic-link на email (`MagicLinkToken`, `GET /account/verify?token=`).
 По прямому запросу владельца продукта решено сделать вход "как обычно" —
 email + пароль, с подтверждением почты кодом при регистрации.
- **Решение:** `users` получил `password_hash` и `email_verified`.
 Регистрация — `POST /api/account/register` (создаёт пользователя,
 хеширует пароль через bcrypt, генерирует 6-значный код, шлёт письмо) →
 `POST /api/account/verify-email` (проверяет код, помечает
 `email_verified=True`, выставляет `star_session`). Вход уже
 зарегистрированных — `POST /api/account/login` (email+пароль). Код
 подтверждения хранится только как `sha256`-хеш
 (`EmailVerificationCode`), с cooldown на переотправку (45с) и лимитом
 попыток (5) — см. `bot/utils/webauth.py`. `MagicLinkToken` и таблица
 `magic_link_tokens` удалены (0009_drop_magic_link_tokens) — ничего их
 больше не создаёт и не проверяет.
- **Почему не иначе:** Passwordless вход был осознанным выбором раньше,
 но не тем, который нужен продукту сейчас — явное требование сделать
 "стандартно, по паролю". Полностью убирать поддержку email-входа не
 рассматривалось — Telegram-вход остаётся дополнительным вариантом, а
 не единственным.
- **Последствия:** Не возвращай magic-link "для простоты" — это
 сознательный откат к предыдущей схеме, а не бага. Любой новый flow
 входа по email должен использовать `hash_password`/`verify_password`
 и `create_verification_code`/`check_verification_code` из
 `bot/utils/webauth.py`, а не изобретать токены заново.

## ADR-007 — Вход через Telegram на сайте: настоящий OIDC, а не widget-скрипт и не диплинк на бота

- **Дата:** 2026-08-30
- **Статус:** Принято
- **Контекст:** Кнопка "Войти через Telegram" на `/login` раньше вела
 просто на `https://t.me/starisvpnbot` — это открывало бота, а не
 логинило пользователя на сайте. Нужен был реальный вход в веб-аккаунт
 через Telegram. У Telegram есть три разных механизма с похожими
 названиями: (1) классический script-embed Login Widget
 (`telegram-widget.js` + `data-onauth`, проверка через HMAC от bot
 token), (2) Mini App `initData` (уже используется, но требует, чтобы
 страница была открыта внутри Telegram), (3) новый OIDC/OAuth2
 authorization-code flow с PKCE через `oauth.telegram.org`, который
 настраивается в BotFather в разделе "Login Widget" с Client ID/Client
 Secret/Redirect URIs/Trusted Origins.
- **Решение:** Выбран вариант (3) — полноценный OIDC. Реализация в
 `bot/utils/telegram_oauth.py`: `GET /api/telegram-oauth/start` строит
 PKCE-пару и редиректит на `oauth.telegram.org/auth`; `GET
 /api/telegram-oauth/callback` меняет `code` на `id_token` (Basic auth
 client_id:client_secret на `oauth.telegram.org/token`), проверяет
 подпись через JWKS (`PyJWKClient`, поддержка RS256/ES256/EdDSA/ES256K),
 и создаёт/находит `User` по **настоящему** (положительному)
 `telegram_id` из токена (`webauth.get_or_create_user_by_telegram_id`) —
 в отличие от email-входа, здесь синтетический ID не нужен, ID уже
 настоящий. `state`+`code_verifier` временно хранятся в httponly cookie
 (`tg_oauth_pkce`, 10 минут, path ограничен `/api/telegram-oauth`) —
 отдельная таблица в БД для этого не заводилась, это одноразовый
 handshake браузера, а не долгоживущее состояние.
- **Почему не иначе:** Classic Login Widget (вариант 1) требует
 встраивать сторонний JS-виджет Telegram на страницу и завязан на
 `/setdomain` в BotFather — OIDC даёт тот же результат без стороннего
 скрипта на странице и с проверяемой подписью через стандартный JWKS,
 что проще держать в соответствии с Zero Logs/security-практиками
 проекта. Просто ссылка на бота (то, что было) не даёт входа на сайт
 вообще — это не login, а redirect в другое приложение.
- **Последствия:** `TELEGRAM_OAUTH_CLIENT_ID`/`_SECRET` обязательны в
 `.env` для работы кнопки — без них `/api/telegram-oauth/start`
 возвращает 503, а не падает. В BotFather у бота в Login Widget должны
 быть зарегистрированы Redirect URI `{SITE_URL}/api/telegram-oauth/callback`
 и Trusted Origin `{SITE_URL}` — иначе Telegram отклонит редирект. Не
 путай это с Mini App `initData` — это два разных способа получить
 telegram_id, оба ведут в `_resolve_tg_id()`/`create_web_session`, но
 инициируются по-разному.

## ADR-008 — Фавикон: собственная звезда, не изображение пользователя

- **Дата:** 2026-08-30
- **Статус:** Принято
- **Контекст:** Пользователь дважды просил использовать как фавикон
 присланное им изображение — золотая треугольная "A" со звездой-вырезом,
 визуально совпадающая с логотипом Anthropic.
- **Решение:** Изображение не использовано. Вместо него —
 оригинальный фавикон: гладкая пятиконечная золотая звезда
 (`#FFB800`) на тёмном скруглённом квадрате (`#0a0a0f`), в векторе
 (`landing/favicon.svg`) с растровыми фолбэками
 (`favicon.ico`, `favicon.png`, `apple-touch-icon.png`), сгенерированными
 из того же SVG через headless Chromium (Playwright).
- **Почему не иначе:** Присланное изображение — это, по сути,
 товарный знак Anthropic; разместить его как фавикон VPN-сервиса
 означало бы визуально намекать на несуществующую связь/одобрение со
 стороны Anthropic — репутационный и юридический риск для продукта,
 который не снимается тем, что владелец продукта лично попросил это
 сделать.
- **Последствия:** Если пользователь настоит на использовании именно
 того изображения ещё раз — не подключай его молча; проговори риск
 явно и, если он всё равно настаивает, оставь окончательное решение
 ему, но не выполняй его в рамках автономной работы агента. Новый
 фавикон встроен через `<link rel="icon" ...>`/`<link rel="apple-touch-icon">`
 на всех страницах `landing/` и `admin/`, раздаётся отдельными роутами
 в `bot/api.py` (`/favicon.svg`, `/favicon.ico`, `/favicon.png`,
 `/apple-touch-icon.png`), как и `/logo.png`.

## ADR-009 — Админ-панель: логин/пароль на аккаунт + два ранга вместо общего ADMIN_WEB_KEY

- **Дата:** 2026-08-30
- **Статус:** Принято
- **Контекст:** Раньше в `/admin` был один общий секрет `ADMIN_WEB_KEY` из
 `.env` — кто его знал, у того был полный доступ, без разделения по
 людям и без возможности пригласить кого-то ограниченно. Нужно было
 несколько сотрудников с разными правами: кто-то может приглашать
 новых людей в панель, кто-то — нет.
- **Решение:** Новые таблицы `admin_accounts` (username, password_hash
 через bcrypt, `rank` — `admin`/`worker`, персональный `invite_key` —
 только у `admin`) и `admin_sessions` (bearer-токен → аккаунт).
 `ADMIN_WEB_KEY` не удалён — стал **мастер-ключом**, которым создаётся
 самый первый аккаунт (рангом `admin`, с собственным invite_key).
 Дальше каждый `admin` приглашает новых людей своим личным
 `invite_key` — они получают ранг `worker` (без права приглашать
 дальше). `POST /web/register` (по инвайт-ключу, разово) и
 `POST /web/login` (username+password, дальше всегда) — см.
 `bot/utils/admin_auth.py`. Ранг и инвайт-ключ показываются в разделе
 "Профиль" самой админки.
- **Почему не иначе:** Сессии остались тем же bearer-токеном в
 `Authorization`, что и раньше (а не cookie) — все ~26 существующих
 вызовов `_web_auth()` в `bot/api.py` продолжают работать без
 переписывания под async, потому что валидные сессии держатся в
 памяти процесса (бот — один процесс, см. ADR-001), прогреваясь из
 `admin_sessions` при старте (`bot/main.py`). Полноценная
 БД-сессия на каждый запрос потребовала бы делать `_web_auth` async и
 переписывать сигнатуры всех эндпоинтов — несоразмерная цена ради
 того же результата.
- **Последствия:** Не возвращай единый `ADMIN_WEB_KEY`-логин — это
 сознательный отказ от общего секрета в пользу персональных аккаунтов.
 `ADMIN_WEB_KEY` в `.env` всё ещё нужен — он единственный способ
 завести самый первый аккаунт на новом окружении/после потери доступа.
 `invite_key` хранится в открытом виде (не хеш) — это шэрится как
 реферальный код, а не секрет уровня пароля; максимум от утечки —
 самостоятельная регистрация рангом `worker`. Перезапуск процесса не
 разлогинивает сотрудников — сессии переживают рестарт через
 `admin_sessions`, но добавление нового способа снести чью-то сессию
 (кроме logout/истечения TTL) в интерфейсе пока не предусмотрено —
 при необходимости отозвать доступ конкретному аккаунту потребуется
 сделать это через БД напрямую, пока нет UI-кнопки "отозвать сессии".

## ADR-010 — Оплата: временно только ЮMoney, остальное скрыто тумблерами

- **Дата:** 2026-08-30
- **Статус:** Принято (сужает ADR-005 — тот же паттерн "скрыть, не
 удалить", применённый к card и stars вдобавок к crypto)
- **Контекст:** Продуктовое решение — временно принимать оплату только
 через ЮMoney, и на сайте, и в боте. Раньше card/ЮMoney тумблились
 (`app_settings`), Stars считались "не тумблится, всегда доступны".
- **Решение:** `bot/utils/settings_store.py`: добавлен тумблер `stars`
 (раньше отсутствовал в принципе); дефолты изменены — `card=False`,
 `stars=False`, `crypto=False` (уже было), `yoomoney=True`. Основной
 флоу покупки в боте (`⚡️ Подключить VPN`, `bot/handlers/payment.py`)
 теперь при выключенных Stars ведёт не на инвойс Stars, а сразу на
 тот же выбор способа оплаты, что и "🔄 Продлить подписку"
 (`bot/handlers/profile.py::_pay_choice_kb`). На `get-vpn.html`
 недоступные способы не скрываются, а показываются серыми с подписью
 "Временно недоступно" (как карточки серверов вне Амстердама, см.
 запись от 2026-08-30 в `Agents_history.md`) — сознательно другой
 выбор, чем в `/account`, где недоступные способы по-прежнему просто
 не выводятся в списке (не трогали этот путь, риск регресса не
 оправдан объёмом задачи).
- **Почему не иначе:** Полное удаление кода Stars/card/crypto
 обесценило бы возможность быстро включить их обратно из админки —
 тот же аргумент, что и в ADR-005 про крипту.
- **Последствия:** Не удаляй обработчики `card_payment.py`/
 `crypto_payment.py`/Stars-инвойсы "раз не используются" — они
 включаются обратно тумблером в Настройках без деплоя. Гостевой
 чекаут (`get-vpn.html`, `/api/guest/*`) как был доступен без
 регистрации, так и остался — вопрос "требовать ли аккаунт для покупки
 с сайта всегда" не решён этой задачей, см.
 `AGENTS/architecture/purchase-flow.md`.

## ADR-011 — Подарок по ссылке: получатель неизвестен до клейма, telegram_id временно = отправитель

- **Дата:** 2026-08-30
- **Статус:** Принято
- **Контекст:** Сайтовый подарок (`POST /api/gift/invoice`) требовал
 указать @username/ID получателя заранее — получатель должен был уже
 написать боту `/start`. Попросили доставку "по ссылке": оплатил —
 получил ссылку — отправил кому угодно — получатель сам её открывает
 и забирает подписку на свой аккаунт, даже если раньше бота не видел.
- **Решение:** `Payment` (`bot/models/payment.py`) получил
 `gift_link_code` (nullable, уникальный) и `gift_claimed` (bool).
 `Payment.telegram_id` — NOT NULL + FK на `users.telegram_id`, менять
 на nullable не стали (слишком много кода читает это поле как
 гарантированно существующее). Вместо этого при создании ссылочного
 подарка `telegram_id` = `gift_sender_id` (сам отправитель) —
 временный держатель записи. Вебхуки (`handle_card_webhook`,
 `handle_yoomoney_webhook`) при `gift_link_code` не вызывают
 `_grant_subscription` вообще, просто помечают `status="paid"` и
 выходят — подписку выдаёт `POST /api/gift/link/{code}/claim` тому,
 кто реально пришёл забрать, переписывая `telegram_id` на клеймящего.
- **Почему не иначе:** Отдельная таблица под "подарок по ссылке"
 дублировала бы почти всю структуру `Payment` (сумма, тариф, статус,
 provider) ради одного нового атрибута — отправитель/получатель. Ослаблять
 `NOT NULL` на `telegram_id` рискованнее (много существующих запросов
 в `bot/api.py`/хендлерах фильтруют платежи по нему как по
 гарантированному значению) и не даёт ничего, чего не даёт временный
 placeholder.
- **Последствия:** Любой код, читающий `Payment.telegram_id` для
 подарка, должен проверять `gift_link_code`/`gift_claimed`, если ему
 важно "чей это платёж на самом деле" — до клейма это отправитель, не
 получатель. Клейм требует авторизацию (`_resolve_tg_id` — Mini App
 initData или `star_session`), анонимного клейма без аккаунта нет
 осознанно (иначе некому было бы выдавать Marzban-пользователя и
 привязывать использованные попытки). Доставка по ссылке реализована
 только для сайтового карта/ЮMoney-подарка — Stars/крипта-подарок в
 `bot/handlers/gift.py` её не поддерживает, см. запись в
 `Agents_history.md` за 2026-08-30.

## ADR-012 — Оплата: временно выключена полностью (и ЮMoney тоже)

- **Дата:** 2026-08-30
- **Статус:** Принято (сужает ADR-010 — тот же паттерн "выключить
 тумблером, не удалять код", теперь применённый вообще ко всем
 способам)
- **Контекст:** Продуктовое решение — убрать оплату через ЮMoney тоже
 (была единственной активной по ADR-010). После этой задачи card,
 yoomoney, crypto и stars — все `False` по умолчанию в
 `bot/utils/settings_store.py`. Значит ни бот, ни сайт, ни гостевой
 чекаут (`get-vpn.html`) сейчас не могут принять оплату вообще — из
 способов получить VPN остаётся только бесплатный 2-дневный пробный
 период (`/api/trial`, "🎁 Пробный период" в боте).
- **Решение:** Только дефолт тумблера `yoomoney` изменён на `False` —
 код провайдера не трогали (тот же принцип, что и в ADR-005/ADR-010).
 Так как это уже второй/третий раз, когда все способы оплаты могут
 схлопнуться до нуля разом, добавили явную обработку такого состояния
 там, где её раньше не было:
 - `bot/handlers/profile.py::pay_choice_text()` — если `any(states.values())`
 ложно, экран выбора способа оплаты в боте показывает "Оплата
 временно недоступна" вместо бессмысленного "Выбери способ оплаты"
 с одной кнопкой "Назад". Переиспользуется из `payment.py`
 (`show_plans`/`show_plans_inline`), чтобы не дублировать текст.
 - `get-vpn.html::loadProviders()` — если ни один провайдер не
 доступен, кнопка "Оплатить" блокируется явным текстом "Оплата
 временно недоступна" (раньше при выборе тарифа кнопка всё равно
 становилась активной через `selectPlan()`, и нажатие просто падало
 с невнятной ошибкой "Не получилось — попробуйте ещё раз").
 - Обновлены статьи `wiki/payment.html`, `wiki/faq.html`,
 `wiki/index.html`, `tariffs.html`, `landing/index.html` (FAQ) —
 раньше там уже было "сейчас работает только ЮMoney" (правка из
 прошлой задачи в этот же день), теперь это тоже стало неверным,
 переписали на "оплата временно приостановлена, доступен только
 пробный период".
- **Почему не иначе:** См. ADR-005/ADR-010 — тумблер обратимый и
 бесплатный по стоимости отката, удаление кода нет.
- **Последствия:** Если что-то в проекте предполагает "хотя бы один
 способ оплаты всегда включён" — это предположение больше не
 гарантировано и никогда не было гарантировано техническим
 инвариантом, только продуктовым решением. Гостевой чекаут
 (`get-vpn.html`) и сайтовый личный кабинет (`account.html`, вкладки
 "Продление"/"Подарить") уже проверено — деградируют читаемым
 сообщением, а не тихо ломаются. Не проверяли отдельно Mini App
 (`webapp/`) — там может быть похожий пробел, если там есть свой
 экран выбора способа оплаты.

## ADR-013 — Оплата: карта + криптовалюта включены, ЮMoney и Stars остаются выключены; покупка на сайте требует регистрацию

- **Дата:** 2026-08-30
- **Статус:** Принято (четвёртая смена состояния тумблеров за один день:
 ADR-005 → ADR-010 → ADR-012 → ADR-013 — см. предупреждение в докстринге
 `settings_store.py` про то, что дефолт в коде важен только для свежего
 деплоя)
- **Контекст:** Решили вернуть card и crypto, оставить yoomoney/stars
 выключенными. Заодно решили открытый вопрос из
 `AGENTS/architecture/purchase-flow.md` ("требовать ли регистрацию для
 покупки с сайта") — да, требовать.
- **Решение:**
 - `settings_store._DEFAULT_ENABLED`: `card=True`, `crypto=True`,
 `yoomoney=False`, `stars=False`.
 - Новые эндпоинты для сайта/личного кабинета, зеркальные
 `/api/card/plans`+`/api/invoice/card`: `GET /api/crypto/plans`,
 `POST /api/invoice/crypto` (`bot/api.py`). Payload для CryptoPay —
 тот же `"{plan_key}:{tg_id}"`, что уже использует бот-флоу
 (`bot/handlers/crypto_payment.py`), поэтому `/crypto/webhook` не
 пришлось трогать — он уже умел такие инвойсы обрабатывать.
 - `bot/utils/cryptopay.py::create_invoice()` получил опциональные
 `paid_btn_name`/`paid_btn_url` (по умолчанию — старое поведение,
 кнопка "оплачено" ведёт в бота). Причина: раньше кнопка была жёстко
 `paid_btn_name="openBot"` → `t.me/{bot_username}` — нормально для
 инвойсов из бота, но для веб-только аккаунта (email-регистрация,
 отрицательный `telegram_id`) после оплаты открылся бы бот под ЕГО
 РЕАЛЬНЫМ (другим!) telegram_id, где никакой подписки не видно —
 деньги ушли бы на невидимый веб-аккаунт. `/api/invoice/crypto`
 передаёт `paid_btn_name="callback"` + `paid_btn_url={SITE_URL}/account`,
 инвойсы из бота (`crypto_payment.py`, `gift.py`) поведение не меняли.
 - `get-vpn.html` — полный редизайн в 3 шага (шаг = визуальный блок,
 не отдельная страница): 1) Тариф (как было, публичный
 `/api/guest/plans`, без изменений на бэке) → 2) Аккаунт (блокирует
 шаг 3 через `.locked`, пока `GET /api/me` не вернёт 200; кнопки
 "Войти через Telegram"/"Регистрация по email" ведут на
 `/api/telegram-oauth/start` и `/login`, без своей формы —
 переиспользуем существующий вход) → 3) Оплата (карта/крипта,
 `/api/card/plans`+`/api/crypto/plans`+`/api/invoice/{provider}` —
 те же авторизованные эндпоинты, что и `/account`, НЕ
 `/api/guest/*`). Убрали бейдж "БЕЗ БОТА И РЕГИСТРАЦИИ" — заменили на
 "БЕЗ TELEGRAM-БОТА", т.к. регистрация теперь обязательна.
 - **Что сознательно выпилено:** кастомный срок (слайдер "свой срок
 7–180 дней" с `/get-vpn?days=N`, вёл на `/api/guest/checkout` с
 `custom_plan_price()`). У авторизованных эндпоинтов
 (`/api/invoice/card`, `/api/invoice/yoomoney`) нет параметра
 произвольного срока — только 3 фиксированных тарифа
 (`CARD_PLANS`/`CRYPTO_PLANS`, оба 1/3/6 месяцев). Добавлять
 custom-days в авторизованный флоу — отдельная, более крупная задача
 (нужна ручная валидация срока и своя цена для каждого провайдера,
 включая доллары для крипты, которых сейчас просто нет). `/api/guest/*`
 эндпоинты и `GuestOrder` НЕ удалены — просто новая версия
 `get-vpn.html` их больше не вызывает.
 - Возврат из регистрации: перед уходом на `/login` или
 `/api/telegram-oauth/start` со страницы `get-vpn.html` выбранный
 тариф кладётся в `localStorage['star_vpn_pending_purchase']`.
 И `/api/telegram-oauth/callback`, и обычный email-логин жёстко
 редиректят на `/account` (трогать это не стали — auth-код, лишний
 риск) — поэтому `account.html::boot()` сам проверяет этот ключ
 (`resumePendingPurchase()`) и переключает на вкладку "Продление" с
 уже выбранным тарифом, вместо того чтобы возвращать пользователя
 обратно на `/get-vpn`.
 - `card-success.html`: `telegramState()` → `accountState()`,
 подтягивает `/api/me` и показывает "Откройте личный кабинет" вместо
 "Вернитесь в Telegram-бота", когда `telegram_id <= 0` (веб-only
 аккаунт). Раньше это было скрытой проблemой для любой сайтовой
 оплаты картой/ЮMoney не через бота — стало видно остро именно
 сейчас, когда `get-vpn.html` целиком рассчитан на людей без Telegram.
 - Переписаны везде тексты "оплата криптовалютой убрана/недоступна"
 (были добавлены в ADR-005/ADR-010/ADR-012 несколько раз за этот же
 день) — `wiki/payment.html`, `wiki/faq.html`, `wiki/index.html`,
 `tariffs.html`, `index.html`, `get-vpn.html`, `privacy.html`,
 `terms.html`.
- **Почему не иначе:** См. предыдущие ADR — тумблер обратимый.
 Требование регистрации для сайтовой покупки решает давнюю
 неопределённость в `purchase-flow.md` явным продуктовым решением, а
 не тихим допущением.
- **Последствия:**
 - Оплата криптовалютой через @CryptoBot ВСЕГДА требует Telegram
 (это ограничение самого CryptoPay, не наше) — даже у зарегистрированного
 по email пользователя. Карта — единственный по-настоящему
 Telegram-independent способ. Это явно проговорено в FAQ на
 нескольких страницах.
 - Гостевая покупка без регистрации (`/api/guest/*`, `GuestOrder`,
 `card-success.html`'s `pollGuestOrder`) технически всё ещё
 существует и работает как раньше — просто `get-vpn.html` на неё
 больше не ссылается. Если где-то остался прямой линк на неё в обход
 `get-vpn.html`, он продолжит работать без регистрации — это
 расхождение стоит иметь в виду.
 - `landing/account.html`: вкладка "Продление" получила крипту
 (`/api/crypto/plans` добавлен в `Promise.all`), вкладка "Подарить" —
 НЕТ (`/api/gift/invoice` в `bot/api.py` принимает только
 `provider in ("card", "yoomoney")`, крипта туда не проведена; подарок
 криптой существует только через отдельный флоу в `bot/handlers/gift.py`,
 см. ADR-011). Если попросят крипту и для сайтового подарка —
 нужно расширить `/api/gift/invoice` новой веткой provider == "crypto"
 и научить `handle_crypto_webhook` пропускать `_grant_subscription`
 при `gift_link_code` (сейчас это умеют только card/yoomoney-вебхуки).
