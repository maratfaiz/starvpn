# 📐 ADR — Architecture Decision Records

Здесь фиксируются решения вида "мы специально сделали X, а не Y, потому
что Z" — чтобы следующий агент не "исправлял" осознанный выбор, приняв
его за случайную недоработку.

**Формат новой записи:**
```markdown
## ADR-00N — <название>
- **Дата:**
- **Статус:** Принято / Пересмотрено (→ ADR-00M)
- **Контекст:** какая была проблема/развилка
- **Решение:** что выбрали
- **Почему не иначе:** что рассматривали и почему отклонили
- **Последствия:** что это значит для будущей разработки
```

Не редактируй чужие записи задним числом — если решение устарело,
добавь новую запись со статусом "Пересмотрено" и ссылкой.

---

## ADR-001 — Один процесс для бота, API и раздачи сайта

- **Статус:** Принято
- **Контекст:** Нужно было решить, разносить ли Telegram-бота, backend
  API и раздачу сайта/админки на отдельные сервисы.
- **Решение:** Всё живёт в одном Python-процессе (`bot/main.py`),
  запускается через `asyncio.gather` (aiogram long polling + uvicorn),
  один Docker-контейнер.
- **Почему не иначе:** Продукт достаточно компактный — разделение на
  сервисы добавило бы сетевые вызовы, отдельные деплои и точки отказа
  без реальной пользы на этом масштабе.
- **Последствия:** Правки сайта/админки не требуют пересборки —
  `_serve_html` читает файлы с диска. Обновление кода бота = один
  `git pull` + рестарт одного контейнера. Не создавай отдельный сервис
  под "ещё один маленький API" — расширяй существующий `bot/api.py`.

## ADR-002 — Веб-аккаунты через синтетический отрицательный `telegram_id`

- **Статус:** Принято
- **Дата:** реализовано в рамках личного кабинета на сайте (магик-линк вход)
- **Контекст:** Нужен был вход на сайт по email, без привязки к
  Telegram — но вся схема БД (Device, Payment, GiftNotification,
  рефералка) была построена вокруг `users.telegram_id` как основного
  ключа.
- **Решение:** `users.telegram_id` остаётся `NOT NULL`. Веб-аккаунт без
  Telegram получает **синтетический отрицательный** `telegram_id`,
  сгенерированный при первом входе по email
  (`webauth._get_or_create_user_by_email`). Реальные Telegram ID всегда
  положительные — коллизий не бывает.
- **Почему не иначе:** Альтернатива — сделать `telegram_id` nullable и
  завести отдельный `web_user_id` — потребовала бы менять внешние ключи
  во всех связанных таблицах и дублировать логику "к какому пользователю
  относится этот объект" в двух вариантах.
- **Последствия:** Проверка "это настоящий Telegram-аккаунт?" —
  `user.telegram_id > 0`. Все существующие эндпоинты, работавшие с
  Telegram-пользователями, автоматически работают и с веб-аккаунтами.
  `_resolve_tg_id()` — единая точка входа, которая скрывает эту деталь
  от остального кода.

## ADR-003 — Сайт и админка: статичный HTML без шаблонизатора и сборки

- **Статус:** Принято
- **Контекст:** Нужно было выбрать технологию для сайта/личного
  кабинета/админки: SPA-фреймворк, серверный шаблонизатор (Jinja2) или
  простой статичный HTML.
- **Решение:** Обычные `.html`-файлы с инлайновыми `<style>`/`<script>`,
  без build step. FastAPI отдаёт их "как есть" с диска.
- **Почему не иначе:** Шаблонизатор/SPA добавили бы шаг сборки и
  зависимость от npm/webpack там, где в этом нет необходимости — эти
  страницы не такие уж динамические, а быстрая правка "открыл файл →
  поправил → сразу на проде" ценнее.
- **Последствия:** Дизайн приходит в виде готовых макетов и
  переносится вручную в существующие файлы (не генерируется шаблоном).
  Не добавляй сборку для `landing/`/`admin/` без отдельного обсуждения —
  см. `AGENTS/roles/frontend.md`.
- **Исключение:** Telegram Mini App (`webapp/`) — это React-проект,
  потому что там реально нужна интерактивность уровня SPA. `webapp/app.html`
  — собранный артефакт, который коммитится в git вместе с исходниками.

## ADR-004 — Zero Logs как жёсткое требование, не настройка

- **Статус:** Принято
- **Контекст:** Продукт позиционируется как приватный VPN — нужно
  решить, насколько строго это применяется технически.
- **Решение:** `infra/xray_config.json` **всегда** имеет
  `"access": "none", "error": "none", "loglevel": "none"`. Нигде в коде
  не логируются IP пользователей, метаданные соединений или трафик.
- **Почему не иначе:** Логирование "для отладки" или "временно"
  создавало бы риск случайно оставить его в проде — поэтому это
  зафиксировано как правило, а не переключаемая опция.
- **Последствия:** Любой PR, который добавляет логирование
  IP/трафика/соединений — блокируется, даже если это "временно для
  дебага". Отлаживай на локальном окружении с явно тестовыми данными.

## ADR-005 — Криптовалюта скрыта из UI, но не удалена из кода

- **Статус:** Принято
- **Контекст:** Оплата криптовалютой (CryptoPay) была реализована, но
  бизнес-решение — временно убрать её из пользовательского интерфейса.
- **Решение:** Код платежей криптой (`bot/utils/cryptopay.py`,
  `/api/invoice/crypto`, `/api/crypto/plans`) остаётся в репозитории.
  Видимость управляется тумблером в `app_settings`
  (`bot/utils/settings_store.py`, ключ `crypto`, по умолчанию `False`).
  Админ может включить обратно через `/admin` → Настройки, без деплоя.
- **Почему не иначе:** Удаление кода означало бы полную переработку при
  возврате функции; тумблер даёт возможность включить/выключить без
  правок кода.
- **Последствия:** Не удаляй крипто-код "раз он не используется" — он
  используется, просто скрыт. Если задача — "убрать оплату криптой" на
  самом деле, уточни у человека: скрыть (уже так) или удалить насовсем.
